# Project Configuration

## Purpose

A project registration tells ADE Control Plane how to supervise one ADE-managed repository without copying ADE's internal delivery configuration.

Project configuration is orchestration metadata only.

## Principles

- configuration must be versioned;
- project identity is stable and explicit;
- repository identity is explicit;
- local workspace details are runner-owned where possible;
- required runner capabilities are declarative;
- quota/scheduling overrides are optional and bounded;
- no secrets in committed project configuration;
- no ADE delivery graph/backlog duplication.

## Conceptual configuration

A possible initial shape:

```yaml
version: 1

project:
  slug: argos
  name: Argos
  repository:
    owner: dokor
    name: argos

scheduling:
  enabled: true
  priority: 80
  requiredRunnerLabels:
    - local

ade:
  adapter: local-runner
  projectRef: argos

runner:
  preferred: raspberry-local
  requirements:
    architecture:
      - arm64
    capabilities:
      - ade

quota:
  policy: default
```

The exact persisted/storage format may evolve; domain semantics should remain stable.

## Project identity

Use a stable internal `project_id` generated by the control plane and a human-readable unique `slug`.

Repository owner/name is metadata and can change without changing internal project identity.

## Repository mapping

Recommended fields:

- owner;
- repository name;
- GitHub numeric repository ID once discovered;
- default branch only if useful for display/integration routing.

GitHub repository mapping is used for routing and authorization, not as the only internal identity.

## Scheduling configuration

### `enabled`

Initial registration state should be explicit.

Persisted runtime state may be:

- enabled;
- paused;
- disabled.

Do not conflate configuration presence with active scheduling permission.

### `priority`

Use a bounded integer range, for example 0–100.

Priority influences ordering only after hard gates pass:

- project enabled;
- ADE reports runnable work;
- quota policy allows dispatch;
- compatible runner available;
- no conflicting lease/security block.

### Required runner capabilities

Declare constraints rather than runner implementation details.

Examples:

- architecture;
- Docker availability;
- browser/e2e support;
- memory class;
- project labels.

The scheduler may then select any compatible runner.

## ADE configuration

The control plane needs only enough information to ask the runner/ADE adapter about this project.

Possible fields:

- adapter kind/version;
- opaque `projectRef` understood by the runner/ADE adapter;
- required ADE capability version.

Do not store:

- ADE delivery graph;
- prompt packs;
- internal agent configuration unless ADE explicitly exposes a control-plane-safe reference.

## Runner-owned local mapping

The runner should maintain the authoritative mapping from logical project reference to canonical local repository/workspace root.

Example runner-local configuration:

```yaml
projects:
  argos:
    root: /srv/ade-runner/projects/argos
    allowedCapabilities:
      - ade.status
      - ade.runnable-work
      - ade.advance
      - ade.apply-decision
```

The control plane should send `projectId/projectRef`, not arbitrary host filesystem paths.

## Secrets

Project configuration may contain **secret references**, never secret values.

Examples:

```yaml
githubCredentialRef: github-app-main
providerCredentialRef: codex-account-main
```

Actual secrets are injected into the component that owns them.

## Validation

Registration must reject:

- unsupported config version;
- duplicate slug/repository identity conflicts;
- invalid priority range;
- unknown adapter;
- impossible runner capability schema;
- secret-looking values in fields intended only for references where detectable;
- direct host absolute paths in control-plane-managed configuration if runner-local mapping is the selected design.

## Onboarding flow

Suggested Dashboard flow:

1. enter/select GitHub repository;
2. choose project slug/name;
3. verify ADE project reference through runner capability check;
4. inspect compatible runners;
5. set priority;
6. save project disabled or paused initially;
7. run read-only `ade.status` health check;
8. explicitly enable scheduling.

The first registration should not immediately start privileged development work before configuration/health verification succeeds.

## Removal

Prefer disabling/archiving a project over destructive deletion while executions/audit history reference it.

A project cannot be deleted while:

- active leases exist;
- non-terminal executions exist;
- recovery/reconciliation is pending.
